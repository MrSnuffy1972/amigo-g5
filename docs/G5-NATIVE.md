# G5 native: lifting the games out of the Amiga memory model

Written 30 Oct 2026. This file is the authority for the native milestones (N1 onwards).

## Decided by Karl
- **30 Oct 2026**: "Our games should not be simulating or emulating the RAM structures of the Amiga. We should be
  running natively." Chosen path: **lift step by step**. The translated build stays as the oracle that proves every
  change; each game is lifted piece by piece into native Rust with its own data structures, presentation, sound and
  input first, then the game logic. Games stay playable throughout.
- The 14 Oct and 17 Oct rulings still stand: no emulated hardware, clean-sheet modern code, translated code only an
  intermediate step.

## Where G5 is today (measured 30 Oct 2026)
- Each game's 68000 code is translated instruction by instruction into Rust (`translated.rs`, generated by
  `kit/amigo/port/m68k2rs.py`): game 296 is 20,722 lines in 41 functions, 336 is 32,276 in 50, 608 is 566,844 in 876.
- Every translated instruction works on `Cpu` (the 68000 register file and flags) and `GuestMemory` (one byte array laid
  out like the Amiga's chip and slow RAM). The clean-sheet display, blitter, Paula and CIA code is native Rust, but it
  reads bitplanes, copper lists and samples out of that guest memory.
- So G5 is compiled native code with no emulator loop, but the **game logic and its data are still in Amiga form**.
  That is what the native milestones remove.

## What "native" means here (the finish line for a game)
1. No `GuestMemory`, no 68000 register file, no Kickstart, no custom-chip registers in the shipped game.
2. Game state lives in typed Rust structs (player, enemies, level, score, timers) with names recovered from the code.
3. Drawing is a list of game-level draw calls (sprite at x,y; tile map; text; palette) rendered by a modern renderer,
   not bitplanes and copper lists.
4. Sound is game-level events (play sample S on channel C at pitch P; music track T) mixed natively.
5. Input is read as abstract actions (left, fire, start), not joystick port bits.
6. The lifted game produces the **same frames and sound as the oracle** for the same inputs (the G5 gate), allowing only
   the presentation differences Karl approves (for example smoother scaling).

## Method: the oracle and the strangler
- The current translated build is the **oracle**. It is never shipped once a game is fully lifted, but it is kept in
  the repo's test tooling to check every step.
- A lifted piece replaces translated code behind a seam. At each step the game still runs end to end, and a
  differential test runs oracle and lifted builds side by side on the same scripted input, comparing frames, audio,
  and (while both exist) the game-state values the lifted code owns.
- Each lifted function gets its own differential test: same input state in, same output state and side effects out,
  over recorded real states plus randomised ones.
- AI (Claude Code sessions) does the lifting; the tests decide. A lifted piece that fails a test is not merged.

## Native milestones
Pilot game: **296 Global Thermonuclear Warfare** (the smallest: 41 translated functions). Then 336, then 608.

### N1: the memory and call map (tooling, no game behaviour change)
- Instrument the oracle to record, per translated function, which guest memory ranges it reads and writes, which
  custom registers it touches, and the call graph (JSR/BSR/RTS, jump tables).
- Classify every touched range: bitplanes, sprite data, copper lists, audio samples, game state, constant tables,
  stack, OS structures. Write the map as a versioned JSON report plus a short human summary per game.
- Tests on synthetic programs. Ryzen runs it on the real game (game bytes never enter the repo).

### N2: native presentation
- Recover what the game draws (screens, bobs or sprites, tiles, text, palette changes) from the N1 map, and emit
  game-level draw calls at the points where the game writes to the display.
- A native renderer draws them. The oracle comparison stays exact for the pilot's 600-frame G5 run.
- Once it passes, the bitplane, copper and blitter path is no longer used by this game.

### N3: native sound and input
- Sound: game-level sample and music events into a native mixer; the 44.1 kHz output matches the oracle within the G3
  tolerance.
- Input: the game reads abstract actions; the joystick, keyboard and CIA port reads are gone for this game.

### N4: game state and logic, function by function
- Introduce typed state structs for the game-state ranges from N1. Translated functions reach them through shims, so
  both worlds share one copy of the state.
- Lift functions one at a time into idiomatic Rust on the typed state, leaves of the call graph first, each with its
  differential test. Track progress as lifted functions over total, and lifted bytes of state over total.

### N5: remove the Amiga
- When every function and state range of the pilot is lifted, delete the guest memory, the register file and the
  Kickstart loading from that game's build, keep the oracle in test tooling, and pass the G5 gate.
- Then repeat N1 to N5 for 336 and 608, reusing what generalises (the renderer, mixer, input layer and lifting tools).

## For Ryzen
- G2 crash chasing (the Kickstart patch work of 29 Oct) is paused: those crashes live in the memory model that this
  plan removes. G2 stays as the oracle's own check.
- Ryzen runs each N milestone's tooling on the real game files and keeps the reports outside the repo.

### Layout

- `rust/native_engine/`: the engine crate, and the root of its own Cargo workspace (members `.`, `../games/*`,
  `../games/*/android`). The G5 workspace in `rust/Cargo.toml` excludes it, so the frozen G5 build is untouched.
- `rust/games/gNNN/`: one crate per game (library `gNNN`, desktop binary `gNNN`, `examples/headless.rs`, `tests/`).
- `rust/games/gNNN/android/`: a `cdylib` named `main` that exports `SDL_main` and calls the engine's platform layer.
- `tools/native_package.sh`: builds the Android APK (arm64-v8a and armeabi-v7a, signed as `g5_package.sh` does) and
  the Linux and Windows desktop binaries for a native game.
- Asset extractors, packs, reference runs and function maps live outside the repo (on Ryzen under
  `/srv/bulk/amigo-native/NNNNN/` and `/srv/fast2/native/`); no game bytes, assets or disassembly enter git.

### Engine API (native_engine)

Nothing in the engine knows about the Amiga. Its tests use synthetic data only.

- `game`: `GameInfo {title, id, width, height, tick_hz, bindings, sheet, effect_voices}`, `Options {seed}`,
  `Ctx {input, audio, save, tick}`, `Flow {Continue, Quit}`, trait `Game { tick(&mut Ctx) -> Flow; render(&mut Frame);
  state() -> Vec<(String, i64)> }`, and `Spec {info, make: fn(&Pack, &Options) -> Result<Box<dyn Game>, String>}`.
  `state()` is the named state the verification compares with the original.
- `timing::FixedStep`: the fixed logic rate (50 Hz for PAL) paced against the display rate. On a 60 Hz screen a
  frame is drawn every refresh and the game ticks 50 times a second.
- `gfx`: `Palette` (12-bit Amiga-style colours via `rgb12`, or 24-bit), `Bitmap` (8-bit indexed pixels; `blit`,
  `blit_masked`, `blit_keyed`, `blit_with` for custom per-pixel rules, `line`/`line_with`), `Sheet` (frames of one
  image), `Font` (fixed-cell bitmap fonts, ink, opaque or layer modes) and `Frame` (the indexed picture plus its
  palette; `to_argb`).
- `audio::Mixer`: voices 0 to 3 belong to the music player, the rest to effects. `start`/`play` a `Sample` or
  `Block` with an optional queued `next` block (looping as Paula did), `set_rate`, `set_volume`, `stop`,
  `is_playing`, stereo pan. The game calls `Mixer::tick()` itself where its original called the replayer (it returns
  true on a new row, which some games' timing depends on); the platform never ticks the music.
- `tracker`: a complete ProTracker 2 replayer (`Tracker`, `TrackerTables`), quirks kept. The period, vibrato and
  funk tables come from the game's pack, not from the engine.
- `input`: abstract `Action`s (Up, Down, Left, Right, Fire, Fire2, Start, Cancel, Primary, Secondary, Pause),
  `InputState {held, pressed, released, motion, absolute}`, `Bindings` (`pointer_game()`, `joystick_game()`) from
  host events (keys, pad buttons and axes, mouse, touch, TV remote). The `Mapper` latches presses, so a tap that goes
  down and up between two ticks is still seen (this was the "pressing start does nothing" bug on the Shield).
- `save::Save`: a small JSON store per game id.
- `pack::Pack`: the asset pack (below). `palette`, `sheet`, `bitmap`, `font`, `sample(name, rate)`, `music`, `data`.
- `script`: scripted input ("TICK key/pad/axis/mouse/button/pointer ...") for verification runs.
- `headless::Run`: runs a game with no display for N ticks, writing frames, `state.jsonl` and the audio.
- `frontdoor`: the pre-boot menu (M8 to M11a look, Ami-Go badge, controls sheet from `ControlSheet`), pause menu
  and touch overlay (stick, buttons, pointer mode).
- `platform::sdl::app_main(args, embedded_pack, &Spec)` (feature `sdl`): front door, then the game loop with vsync,
  audio queue, pause menu, touch and relative mouse. Flags: `--pack`, `--ticks`, `--out`, `--every`, `--script`,
  `--seed`, `--touch`, `--fullscreen`, `--preboot-shot`. Logs `native ID: N fps drawn, tick T` every 5 s.
- `napack` binary: `napack pack DIR OUT.nap`, `napack list FILE`.

### Asset packs: native-asset-pack/1

Decision: one versioned, engine-neutral format with two forms of the same content. Extractors write the directory
form (easy to inspect and diff); `napack` turns it into the binary form, which the desktop binary and APK embed
(`NATIVE_PACK=path.nap` at build time) or load with `--pack`.

- Directory: `manifest.json` (`format: "native-asset-pack/1"`, `game`, `title`, `assets: [...]`) plus the files.
- Binary `.nap`: `"NAP1"`, u32 version (1), u32 manifest length, the manifest JSON (each asset entry also gets
  `offset` and `len` into the blob area), the asset bytes, then a u64 FNV-1a 64 checksum of everything before it
  (all little-endian).
- Asset kinds: `palette` (JSON `colours` as `#RRGGBB`), `image` (raw 8-bit palette indices, `w` x `h` per frame,
  `frames` side by side), `font` (an image of glyph cells with `glyph_w`, `glyph_h`, `first`, `count`, optional
  `fold_lower`, `alias`, `blank`), `sample` (signed 8-bit PCM, `format` "s8"; the game supplies the play rate),
  `music` (`format` "protracker-mod") and `data` (any JSON the game needs: tables, texts, button lists). It replaces
  the `0.1-proposed` draft. Names must be unique; `Pack` rejects duplicates, an unknown format or version, and a bad
  checksum.

### How a game is structured

- `assets.rs` loads the pack into typed tables once (`Assets::load`), failing loudly on anything missing.
- The game is one struct with typed state and a `Phase` enum. Each original main-program loop becomes a phase;
  each original routine keeps its author's name as a method, so the function map reads straight across.
- `tick` first does what the original's vertical-blank handler did, then runs the main program until it would have
  waited for a frame. Original frame waits become counters. Work the original was too slow to do in one frame keeps
  its measured cost (a `busy` count), so timing matches the reference tick for tick.
- `render` draws the whole frame from state; it never changes state.
- `state` names the values the comparison scripts read from the original's memory.

### How to add the next game

1. Write `extractNNN.py` outside the repo: read the recovered source and files, write
   `/srv/bulk/amigo-native/NNNNN/pack/` and `napack pack` it to `gNNN.nap`. Remove copy protection; keep cracktros as
   an intro piece.
2. Copy `rust/games/g296` to `rust/games/gNNN` (rename the crate, the `android` crate and the ids), add both to the
   workspace members in `rust/native_engine/Cargo.toml`, and rewrite `assets.rs` and the game module from the
   recovered source.
3. Keep a function map (outside the repo) from every recovered routine to its native code; 100% must be accounted
   for, with a reason for each routine not ported.
4. Verify: the same scripted input through the 68000 reference harness and `examples/headless.rs`, then compare
   named state, frames and audio; write down the tolerances. Then a real play test, desktop and Shield.
5. `tools/native_package.sh --game gNNN --pack gNNN.nap --name "Title" --out DIR --android --linux --package
   org.amigo.g5.gNNNNN.nativegame`, install on the Shield beside the translated build, and check fps and screenshots.
6. `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` in
   `rust/native_engine`; the leak check; then `docs/native/gNNN-native.md`.

## Added by native stage 2: game 336 (1 Nov 2026)

Game 336 (Jail Break) is the second game on the engine: `rust/games/g336`, notes in
[native/g336-native.md](native/g336-native.md).

Engine addition (general, additive): `gfx::Frame::direct: Option<Vec<Argb>>`. A game may give a frame as one
colour a pixel, which then replaces the indexed picture in `to_argb` (and so on every platform); a wrong-sized
picture is ignored. For screens with more colours than a palette holds (Jail Break's hold-and-modify title has 544).
Every other frame stays indexed. `Frame::new` sets it to `None`.

Pattern worth reusing for the next games: an original whose frame waits sit deep inside nested routines can keep its
shape. `g336/src/co.rs` runs the main program on its own thread in strict lock-step with the engine's ticks (each
tick hands over that tick's input and waits for the program's next frame wait), so routines read as the original's
and the result is as deterministic as one thread. Dropping the game unwinds the thread. The long work the original
did between waits is a measured cost in frames (`busy`), and a frame interrupt that came during it makes the next
wait return at once, as on the original. Verification-only features: `trace` (a call trace to compare with the
reference harness's call log) and `ref-harness` (the reference harness's conditions: its stand-in OS's instant
one-second delay and no sprites).

## Release builds and revisions

Added 1 Nov 2026. Karl, 1 Nov: "name all the games filenames with a revision number, from now on".

### File names

`<5-digit id>-<title slug>-r<N>.<ext>`, for example `00296-global-thermonuclear-warfare-r2.apk` and
`00296-global-thermonuclear-warfare-r2-windows.zip`. The revision belongs to the game: it starts at 1 and goes up
by 1 for every released build of that game (an APK and a Windows zip built together share one revision). The old
unnumbered files (`g296-native.apk` and so on) stay where they are.

### Where releases live

- Ryzen: `/srv/fast/amigo/native/releases/<id>/`, mirrored to WinPC `F:\openclaw\tmp\nv-release\<id>\`.
- WinPC `F:\Game Source\Amiga\Native Ports` (added 3 Nov 2026): `release.sh` publishes there too (append-only) and runs
  the native checks (G4 Windows under Wine, `native/tools/g4_native.sh`; G5 Android on IntelPC once built). Current
  gate meanings and the R-first rule are in `CLAUDE.md`.
- `releases/releases.json` (format `amigo-native-releases/1`) records every release: `id`, `title`, `revision`,
  `date` (UTC), `commit` (full hash of amigo-g5), `change` (the note), `files` (`name`, `kind` android or windows,
  `bytes`, `sha256`), `pack_sha256`, `native_rev` (what the pre-boot shows), the toolchains, and `superseded` for a
  revision whose file was not kept. `releases/<id>/releases.json` holds the same entries for one game.
- `releases/games.json`: per game the `title`, `slug` and Android `package`. A new game is added from its pack
  manifest's `title` the first time it is released (package `org.amigo.g5.gNNNNN.nativegame`). Game 336 keeps the
  package `org.amigo.g5.g00336.native` its first APK used, so new releases install over it.
- The APK's `versionCode` is the revision and its `versionName` is `rN`.

### Making a release

```
/srv/fast/amigo/native/tools/release.sh ID "change note" [--android-only | --windows-only] [--ref BRANCH]
                                                         [--pack-dir DIR] [--no-mirror]
```

It clones amigo-g5 for the game (`/srv/fast/amigo/native/build/<id>/repo`), checks out the current tip of `main`,
packs the game's asset pack fresh from `/srv/bulk/amigo-native/<id>/pack` with `napack`, builds the Windows zip and
the signed Android APK, takes the next revision, copies both into `releases/<id>/`, records them, and mirrors the
folder to WinPC (`tools/release_mirror.sh ID` repeats only the mirror). The log is
`build/<id>/release-<UTC time>.log`.

Several games can be released at once (the game agents do): each game has its own lock (`releases/<id>/.lock`; a
second release of the same game waits for the first), its own clone, pack and cargo target directories
(`build/<id>/target-host`, `target-windows`, `target-android`), and the JSON files are written under one short
global lock. A failed build records nothing and its revision is used by the next attempt. Nothing is deleted and an
existing release file is never overwritten.

### The Android verification mode (Ami-Go G5)

Added 3 Nov 2026, so the released APK can be judged on picture and sound as the released Windows exe is under Wine
(G4). The desktop programs always had the headless verification run (`--ticks N --out DIR [--script FILE] [--every K]
[--seed N]`, the same `headless::run` as `examples/headless.rs`), and the Android library always compiled it in, but
nothing could reach it: SDL's activity passed no arguments and `SDL_main` ignored them.

- `tools/native_package.sh` writes `GameActivity.getArguments()`: when the activity is started with the string extra
  `amigo_verify` it returns those options, with `@FILES@` replaced by the app's external files folder; only `--ticks`,
  `--out`, `--every`, `--script` and `--seed` are accepted (anything else, or no `--ticks`, gives no arguments). A
  normal start (launcher, TV, Shield) has no extra and so no arguments: play is unchanged.
- Every game's `android/src/lib.rs` passes SDL's arguments on (`platform::sdl::c_args`, which drops SDL's
  `app_process`), so `app_main` sees `gNNN --ticks ...` and runs headless with the APK's own `gamepack.bin`, writing
  `fNNNNN.rgba`, `state.jsonl` and `audio.raw` into the files folder, then returns; SDL then finishes the activity.
- Example: `adb shell am start -n <package>/org.amigo.GameActivity --es amigo_verify '--ticks 300 --out @FILES@/t1
  --script @FILES@/t1.txt --every 50 --seed 0'`. Checked 3 Nov 2026 on game 296 (API 30 x86_64 emulator, arm64
  code through ARM translation): state, audio and frames byte-identical to the Linux headless runner.
- Every APK built by `release.sh` from this commit on carries it. Ryzen's `native/tools/g5_native.sh` runs it in the
  IntelPC emulator on the golden input; an older APK is reported as blocked (no `amigo_verify` in its dex).

### Toolchains (all under /srv/fast, none on Ryzen's boot drive)

- Windows: llvm-mingw 20261020 (UCRT, `/srv/fast/tools/llvm-mingw`, clang 23.1.4), a rustup toolchain in
  `/srv/fast/tools/rust` (`. /srv/fast/tools/rust/env.sh`; stable with `x86_64-pc-windows-gnullvm`), and the
  official SDL2 2.30.9 mingw development package (`/srv/fast/tools/sdl2-mingw`, the same SDL version as the
  Android build). Download checksums are in `/srv/fast/tools/dl/SHA256SUMS`.
- Android: unchanged, the `amigo-tools:4` image (NDK 26.3, SDL2 2.30.9) with the Rust in `/srv/fast/rust`, signed
  with the image's debug keystore as `tools/g5_package.sh` does.

### The Windows build

- `tools/native_package.sh --windows` builds on the host: `x86_64-pc-windows-gnullvm`, linked with llvm-mingw against
  the SDL2 import library, `crt-static`, so the exe needs only `SDL2.dll` and the UCRT that Windows 10 and 11 ship.
- Decision: the asset pack is embedded in the exe (`NATIVE_PACK`), as on Linux. That also selects the Windows GUI
  subsystem (no console window). The zip holds one folder `<base>-windows/` with `<id>-<slug>.exe`, `SDL2.dll`,
  `README.txt`, `README-SDL.txt` and `SDL2-LICENSE.txt`.
- The pre-boot menu is the front door, as on every platform. Keyboard, mouse and gamepad come from the engine's SDL
  layer (SDL game controllers, hot-plugged).
- Renderer: on Windows the engine asks SDL for `direct3d12` unless `SDL_RENDER_DRIVER` is set. Measured on WinPC on
  1 Nov 2026: SDL 2.30.9's default `direct3d` (Direct3D 11) renderer, Direct3D 9 and `opengl` gave a black or white
  window, while `direct3d12` and `software` drew the pre-boot and the game. SDL falls back to its other renderers if
  Direct3D 12 cannot start.
- Testing on WinPC: copy the zip's folder to `F:\openclaw\tmp\nv-win\<name>\`, start the exe, and capture the window
  (PrintWindow with full content); synthetic clicks and keys sent from a background shell do not reach the window, so
  the auto-start after the countdown is what the scripted check sees.
