# G5 native: lifting the games out of the Amiga memory model

Written 30 Oct 2026. This file is the authority for the native milestones (N1 onwards).

## Decided by Karl
- **30 Oct 2026**: "Our games should not be simulating or emulating the RAM structures of the Amiga. We should be
  running natively." Chosen path: **lift step by step**. The translated build stays as the oracle that proves every
  change; each game is lifted piece by piece into native Rust with its own data structures, presentation, sound and
  input first, then the game logic. Games stay playable throughout.
- The 14 Oct and 17 Oct rulings still stand: no emulated hardware, clean-sheet modern code, translated code only an
  intermediate step.

## Where G5 is today (measured 30 Oct 2026)
- Each game's 68000 code is translated instruction by instruction into Rust (`translated.rs`, generated by
  `kit/amigo/port/m68k2rs.py`): game 296 is 20,722 lines in 41 functions, 336 is 32,276 in 50, 608 is 566,844 in 876.
- Every translated instruction works on `Cpu` (the 68000 register file and flags) and `GuestMemory` (one byte array laid
  out like the Amiga's chip and slow RAM). The clean-sheet display, blitter, Paula and CIA code is native Rust, but it
  reads bitplanes, copper lists and samples out of that guest memory.
- So G5 is compiled native code with no emulator loop, but the **game logic and its data are still in Amiga form**.
  That is what the native milestones remove.

## What "native" means here (the finish line for a game)
1. No `GuestMemory`, no 68000 register file, no Kickstart, no custom-chip registers in the shipped game.
2. Game state lives in typed Rust structs (player, enemies, level, score, timers) with names recovered from the code.
3. Drawing is a list of game-level draw calls (sprite at x,y; tile map; text; palette) rendered by a modern renderer,
   not bitplanes and copper lists.
4. Sound is game-level events (play sample S on channel C at pitch P; music track T) mixed natively.
5. Input is read as abstract actions (left, fire, start), not joystick port bits.
6. The lifted game produces the **same frames and sound as the oracle** for the same inputs (the G5 gate), allowing only
   the presentation differences Karl approves (for example smoother scaling).

## Method: the oracle and the strangler
- The current translated build is the **oracle**. It is never shipped once a game is fully lifted, but it is kept in
  the repo's test tooling to check every step.
- A lifted piece replaces translated code behind a seam. At each step the game still runs end to end, and a
  differential test runs oracle and lifted builds side by side on the same scripted input, comparing frames, audio,
  and (while both exist) the game-state values the lifted code owns.
- Each lifted function gets its own differential test: same input state in, same output state and side effects out,
  over recorded real states plus randomised ones.
- AI (Claude Code sessions) does the lifting; the tests decide. A lifted piece that fails a test is not merged.

## Native milestones
Pilot game: **296 Global Thermonuclear Warfare** (the smallest: 41 translated functions). Then 336, then 608.

### N1: the memory and call map (tooling, no game behaviour change)
- Instrument the oracle to record, per translated function, which guest memory ranges it reads and writes, which
  custom registers it touches, and the call graph (JSR/BSR/RTS, jump tables).
- Classify every touched range: bitplanes, sprite data, copper lists, audio samples, game state, constant tables,
  stack, OS structures. Write the map as a versioned JSON report plus a short human summary per game.
- Tests on synthetic programs. Ryzen runs it on the real game (game bytes never enter the repo).

### N2: native presentation
- Recover what the game draws (screens, bobs or sprites, tiles, text, palette changes) from the N1 map, and emit
  game-level draw calls at the points where the game writes to the display.
- A native renderer draws them. The oracle comparison stays exact for the pilot's 600-frame G5 run.
- Once it passes, the bitplane, copper and blitter path is no longer used by this game.

### N3: native sound and input
- Sound: game-level sample and music events into a native mixer; the 44.1 kHz output matches the oracle within the G3
  tolerance.
- Input: the game reads abstract actions; the joystick, keyboard and CIA port reads are gone for this game.

### N4: game state and logic, function by function
- Introduce typed state structs for the game-state ranges from N1. Translated functions reach them through shims, so
  both worlds share one copy of the state.
- Lift functions one at a time into idiomatic Rust on the typed state, leaves of the call graph first, each with its
  differential test. Track progress as lifted functions over total, and lifted bytes of state over total.

### N5: remove the Amiga
- When every function and state range of the pilot is lifted, delete the guest memory, the register file and the
  Kickstart loading from that game's build, keep the oracle in test tooling, and pass the G5 gate.
- Then repeat N1 to N5 for 336 and 608, reusing what generalises (the renderer, mixer, input layer and lifting tools).
